## Namecheap: corrected first-party SDK evidence (2026-11-09 follow-up)

**Decision correction:** the original website-only analysis below is superseded where it claimed mail/status/transport/cap evidence was unavailable. A real narrowly scoped all-active BasicDNS implementation is now integrated and locally verified; its exact current scope/counts are in [full progress](<../PROVIDERS.md>). Broad arbitrary-zone preservation is still unproved.

- The [Namecheap-maintained SDK mail contract](https://github.com/namecheap/go-namecheap-sdk/blob/master/namecheap/domains_dns_email_type.go) explicitly states that **omitting EmailType preserves the current zone mode**, dated sandbox and production 2026-10-08. The website's Required Yes table is inconsistent with this vendor-published contract. [Merged PR #199](https://github.com/namecheap/go-namecheap-sdk/pull/199) documents synthesized FWD/OX/GMAIL mail records absent from getHosts; do not reconstruct or change that mail mode.
- The [first-party getHosts XML fixture](https://github.com/namecheap/go-namecheap-sdk/blob/master/namecheaptest/fixtures/domains_dns_getHosts.xml) exposes EmailType and row IsActive/IsDDNSEnabled/AssociatedAppTitle/FriendlyName. getInfo's SDK model additionally exposes DnsDetails HostCount/EmailType/DynamicDNSStatus/IsFailover. Missing controls are rejected rather than guessed.
- [SDK transport](https://github.com/namecheap/go-namecheap-sdk/blob/master/namecheap/namecheap.go) uses URL-encoded form POST for globals and indexed records. XML is the response format, not the request body. The confusing website JSON example is not a reason to categorically block form POST.
- [Official DNS limits](https://www.namecheap.com/support/knowledgebase/article.aspx/10058/10/namecheap-dns-limits/) and [BasicDNS documentation](https://www.namecheap.com/support/knowledgebase/article.aspx/923/10/what-is-your-basicdns/) publish the **800-record ceiling**. HostCount equality semantics for synthesized records remain uncertain; a supplied mismatch rejects the narrow snapshot rather than excluding invisible records to force equality.
- Provenance is independently supported by [Namecheap's own Terraform article](https://www.namecheap.com/blog/lets-talk-about-terraform/), linking its maintained provider whose module depends on this SDK. No vendor acceptance test or real API call was executed in this investigation.

Authorized initial scope: owned registered BasicDNS, explicit production/sandbox and server-public IPv4, explicit whole-zone exclusive-writer consent, only ordinary fully representable A/AAAA/TXT/CNAME/NS/MX rows (MX only under the observed MX mode), every row active/non-DDNS with empty unsupported app/friendly metadata, no failover/Premium DNS. Reject unsupported snapshots before no-op/dry-run/write; omit EmailType, preserve all legal row fields, use stable logical owner/type IDs, fresh full snapshots and strict readback. Broader inactive, app metadata, ALIAS/CAA/redirect/SRV preservation remains outside the initial scope.

## Namecheap: original website-only findings and two different products

**Verified official contract:**

- [Dynamic DNS guide](https://www.namecheap.com/support/knowledgebase/article.aspx/29/11/how-to-dynamically-update-the-hosts-ip-with-an-https-request/) (displayed update 2024-11-19): `https://dynamicdns.park-your-domain.com/update?host=...&domain=...&password=...&ip=...`; "only the GET method"; "only possible to dynamically update IPv4 addresses (A records)". Uses the **domain Dynamic DNS password**, not the account password/API key. Omitting `ip` uses the caller's IP; require an explicit desired IP instead. Domain/host case must match the account. Available for BasicDNS/PremiumDNS/FreeDNS. This is precisely the path used by Go; it has **no documented authoritative record inventory, TTL/settings read, or AAAA update**. Do not declare a completed snapshot adapter using it, DNS lookup, or cached desired state.
- [API introduction](https://www.namecheap.com/support/api/intro/): production `https://api.namecheap.com/xml.response`, sandbox `https://api.sandbox.namecheap.com/xml.response`, separate environment account/key; API enabled under Profile → Tools. "You should whitelist at least one IP ... only IPv4 addresses can be used." [Global parameters](https://www.namecheap.com/support/api/global-parameters/): `ApiUser`, `ApiKey`, `UserName`, `Command`, `ClientIp`; ClientIp is "an IP address of the server from which our system receives API calls (only IPv4 can be used)." Thus configured public **server egress IPv4** and its allowlist entry are prerequisites, not the DDNS target address or a private interface IP. Require explicit environment selection; never probe/fallback across environments. A server-public-IP environment-reference option would need parent approval; it must not silently discover/change the allowlist.
- [API FAQ](https://www.namecheap.com/support/knowledgebase/article.aspx/9739/63/api-faq/): production activation requires ≥20 domains, ≥$50 balance, or ≥$50 spent in the last two years (otherwise support); API key-wide limits 50/min, 700/hour, 8000/day. Explicitly says PremiumDNS/FreeDNS cannot be managed via this API; restrict to owned registered domains using BasicDNS. The Dynamic DNS guide's broader support does **not** override this restriction.
- [getHosts](https://www.namecheap.com/support/api/methods/domains-dns/get-hosts/): "Retrieves DNS host record settings for the requested domain"; `SLD`, `TLD`, result `Domain`, `IsUsingOurDNS`, host `HostId`, `Name`, `Type`, `Address`, `MXPref`, `TTL`. No page request, count/total, or numeric list ceiling documented. Example contains all host elements inside one result, but does not itself establish hidden truncation behavior. Validate exact returned domain and DNS mode. [getInfo](https://www.namecheap.com/support/api/methods/domains/get-info/) supplies ownership/status/DNS-provider evidence, **not mail-mode or per-record activation**.
- [setHosts](https://www.namecheap.com/support/api/methods/domains-dns/set-hosts/): **"All host records that are not included into the API call will be deleted"**; recommends POST for >10 hostnames. Writes indexed `HostName`, `RecordType`, `Address`, `MXPref`, `TTL`; record types include A, AAAA, ALIAS, CAA, CNAME, MX, MXE, NS, TXT, URL, URL301, FRAME. `EmailType` is documented required: MXE/MX/FWD/OX. TTL 60–60000, default 1800; always serialize existing TTL explicitly. CAA `Flag`/`Tag` also appear; their relationship to Address/indexing needs complete roundtrip evidence. Errors 3013288/4013288 mean "Too many records", **not a published numeric ceiling**. The >10 POST advice is not a zone cap. Its unusual JSON POST example is not proof that ordinary XML endpoint form POST and authentication placement are interchangeable; obtain a supported encoding fixture before choosing transport.

**Concrete preservation gap, not an automatic always-blocked design:** documented getHosts response does **not** expose `EmailType` or `isActive`; documented setHosts has **no `isActive` setter**. Neither source proves that real responses lack these fields, that omitted status is preserved, nor that HostId survives replacement. Do not infer mail mode from MX addresses or turn disabled records active. Preserve MX priority and TTL verbatim for every unrelated record; do not default unknown values. Obtain official/current SDK or sanitized vendor-provided request/response fixtures proving (1) complete inventory/count/cap behavior, (2) mail-mode read/write/omit preservation, (3) active/disabled/unsupported record behavior, (4) CAA/redirect/ALIAS preservation, (5) accepted POST representation and identity after replacement. An explicitly constrained **all-active, fully representable BasicDNS snapshot** could be eligible once these guarantees are established; unsupported snapshots fail before writing rather than an adapter unconditionally failing every update.

**Defensible next work:** parent-approved read-only getInfo/getHosts snapshot reader and bounded XML decoder can be implemented from these documented contracts; mutation must await the above evidence. Full-zone replacement without CAS is permissible **only** with complete field/settings roundtrip, explicit exclusive-writer opt-in, fresh full snapshot, one replacement, and full readback comparison. Exclusive writer is an operational assumption, not a lock/CAS guarantee. Use stable logical singleton host/type IDs if HostId changes; keep actual IDs in opaque metadata and never fabricate API IDs. Ambiguous duplicates require a defensible identity contract, not "first record".

All three explicitly document GET, HMAC-SHA1, `AccessInstanceID` (described as access-key ID), `SignatureMethod`, UTC `Timestamp`, fresh `SignatureNonce` (≥8 characters in Chinese prose); sort names lexicographically, RFC3986-style encoding (`+`→`%20`, `*`→`%2A`, `%7E`→`~`), `GET&percentEncode("/")&percentEncode(canonicalQuery)`, Base64 HMAC. Resolve with the referenced official `DnsApiTest.php`/signature vector; no automatic signing variants or test-account probing.

Each independently publishes lowercase **`/api/dns/`**:

- `DescribeRecordIndex`: Domain required; "all DNS resolution records". No response schema, page request keys, count/cap, filter contract, or errors documented on these articles.
- `AddDomainRecord`: Domain/Host/Type/Value/Ttl required.
- `UpdateDomainRecord`: those fields plus string Id required. It updates **one native record**, not a whole-zone replacement. The sample simultaneously claims Host-only updates and omits fields marked required: omission/patch preservation is **unresolved**.
- `DeleteDomainRecord`: Domain/Id; not needed for DDNS.

**Per-provider prerequisites / recommendation:**

- **Now.cn:** current official base differs from Go `https://api.now.cn`; Go also uses `/api/Dns/` and Host/Type filters not documented here; its read model omits TTL/MX and its writes use configured TTL without forwarding State (preservation risk, not a verified server reset), and assumes an empty `error` means success. Obtain Now-specific official SDK or sanitized independent-domain fixtures establishing exact base/case, signature key, success/error payload (including HTTP 200), native ID types/lifecycle, list completeness/page keys and preservation of TTL/MX/state/line fields. This is a promising JSON per-ID adapter after those prerequisites, not a whole-zone adapter or ready implementation.
- **Eranet:** official base independently matches Go, route case and key suffix still conflict; [official DDNS guide](https://help.eranet.com/domain/resolve/20260407170013/) (2026-04-09) explicitly supports IPv4/IPv6, requires contacting customer service to activate the domain management interface, and identifies domain-management API ID/key. Need Eranet-specific response/paging/signature/settings fixture before enabling; do not import Now's response quirks. Closest supported brand-specific onboarding evidence, so **first fixture request recommendation**.
- **Tnet.hk:** own official document confirms its base independently (Eranet prose mentioning a Tnet base is not the evidence relied on). Obtain Tnet-specific success/list/error/signature/page/status fixtures; Go string-ID compatibility is not proof of official wire types. The articles' public Document download links were followed: [Now](https://www.now.cn/support/doc.php), [Eranet](https://www.eranet.com/support/doc.php), [Tnet](https://www.tnet.hk/support/doc.php) resolve to each brand's `/customer/doc.php`. Consequently the Host-only sample versus required Type/Value/Ttl table contradiction and mail/state/settings preservation remain unresolved; a request-only sample, even if found, would not by itself prove the server preserves omitted controls or inventory is uncapped/unpaginated.

### Public Todaynic API-documentation UI evidence is a different contract surface

[Todaynic documentation](https://www.todaynic.com/docApi/) is linked in Now's Go comment and by Now's official help-site reseller navigation. Its HTML loads [main.bundle.js](https://www.todaynic.com/docApi/assets/main.bundle.js?v=1721271554539), retrieved as static source; embedded generator date **2024-07-18**, version 1.0.0. This is official published evidence, **not proven equivalent to any independent-domain endpoint**:

- `/Dns/DescribeRecordIndex` lists IDDomain/Domain/keyword/Host, example `Data` row `{id,domain,host,type,value,ttl,mx,state}` and **`Pagination:{current:1,pageSize:20,total:1}`**. DNS parameter table lacks pagination request controls; other unrelated methods use current/pageSize, which cannot be borrowed as a verified DNS contract. **Do not report a first page as complete, or a filtered empty list as absence.**
- `/Dns/AddDomainRecord` and `/Dns/UpdateDomainRecord` include required `Mx` and `Ttl` (minimum 600); update's Host/Type are optional **with defaults**, not documented preserve-on-omit semantics. Their type list omits AAAA, despite Eranet's independent DDNS guide supporting it. `state` has no semantics/preservation setter established here.
- Successful write examples contain RequestId alone, while Go expects Id/error; no basis for interpreting every JSON object without `error` as success. The legacy [Eranet reseller API introduction](https://partner.eranet.com/partner/mode_Api_detail_en.php) describes SSL **DBRRP**, further evidence that shared ownership/branding does not make every API interchangeable.

A future single transport/signature implementation is possible **after** each brand's scope and vector are established. Preserve native ID, host, type, original TTL and all mutable settings; require singleton selection or exact unambiguous ID. Complete paged snapshots must validate current/pageSize/total, unique IDs, domain, stable totals, count completion, bounded page/record limits, and never silently truncate. Unknown state/line/MX behavior blocks only affected unsupported configurations until its contract is known; no always-failing placeholder adapter.

## Shared implementation requirements (proposal only)

- Existing [Cargo manifest](<../Cargo.toml>) has serde/serde_json, reqwest, hmac/sha1/base64, percent-encoding, sha2; **no XML dependency**. [NameSilo adapter](<../src/providers/namesilo.rs>) intentionally uses documented JSON, not a reusable XML library. Add no dependencies in this task.
- If parent approves Namecheap implementation, a minimal provider-local XML tokenizer can safely cover the documented envelope: cap response bytes, nesting, element/attribute counts and lengths; reject DTD/DOCTYPE/ENTITY, declaration extensions, external resources and unknown entities; permit only a bounded standard XML declaration declaring supported UTF-8, and predefined XML entities and bounded valid numeric character references (never custom entity expansion); validate UTF-8/XML scalar ranges, quoted attributes, duplicate attributes, matching tags, one root, namespace binding/known HTTP or HTTPS Namecheap namespace and exact command/result path. Comments/CDATA, if supported, remain bounded data, never substring success detection. Unknown writable host attributes must not disappear silently. Malformed/truncated XML, duplicate results or namespace spoofing fail before any write. This is a proposal, not an implemented/tested parser.
- Proposed credential prefixes: `NAMECHEAP_` API username/key pair (DDNS password would be a distinct credential/product), `NOWCN_`, `ERANET_`, `TNETHK_` access-instance-ID/secret pairs; generic `DDNS_` scoped aliases follow existing validation. ClientIp is nonsecret configuration/environment reference; environment endpoint must be fixed allowlisted choice. Do not store plaintext credentials, change shared validation, or invent configuration fields here.
- **GET authentication leaks into URLs/proxies/access logs.** Never log full requests, redirect locations or raw errors; disable redirects. Redact raw, form-encoded, percent-encoded upper/lowercase and double-encoded credential values, IDs/usernames as appropriate, and per-request Signature, including echoed values/body diagnostics. HMAC secret is not transmitted, but signature is sensitive. Fixed HTTPS routes, no endpoint/signature fallback.
- HTTP 200 is not success: Namecheap requires `ApiResponse Status=OK`, no Errors, matching requested command/domain and write `IsSuccess=true`; vendors need established typed success/error/code contract (empty/non-JSON bodies and an error-bearing 200 fail). Sanitized method/stage/provider error metadata only. Do not expose URL-bearing reqwest errors.
- Read-only diagnostics call **only** validated inventory/ownership endpoints; GET Add/Update/Dynamic URL is still a write. No create-on-empty/error fallback, implicit mutation for connectivity checks, retry of uncertain writes, or secret-bearing test claims. Snapshot/write/readback verification is API-state evidence, not DNS propagation proof. Where CAS is absent, require exclusive-writer consent and verify complete before/after state, not a fake conditional guarantee.

**New official-client evidence:** the [checksum-verified NowDNS static review](<nowdns-static-contract-review.md>) recovers first-party client code selecting AccessInstanceID and `secret + "&"`, Now's legacy HTTPS base/route case, concrete native State/TTL/Remark fields, and per-ID request fields. Downloaded software was never executed. This improves the old copied-Go/reseller clues but does not prove supported server variants, complete inventory, State semantics or positive mutation acknowledgment; the client ignores State, defaults zero TTL to 600, reads one Data slice and checks only empty error. Do not import those weaknesses or infer cross-brand server equivalence.

**Current documented-route state follow-up:** [independently fetched first-party frontend evidence](<registrar-state-contract-review.md>) on all three brands binds the exact current www/lowercase `GET /api/dns/DescribeRecordIndex` to directly rendered raw Data: **state 0 Normal offers Disable; state 2 Pause offers Enable**, with 3 administrator-pause, 4 review, 5 rejection. There is no State=1 active proof. Direct route matches materially improve state evidence; absence of AccessInstanceID in a session client does not by itself prove a different BFF. However, context/platform/schema dispatch and legacy/capitalized signed route equivalence remain unproved. Frontend list paging uses currentPage/pageSize + Data/Pagination, not verified complete native pages; POST updates forward Mx/Ttl/Line but omit State/Remark, and remark can be a rejection diagnostic. A separate GET Status=Enable/Disable action is not an accepted signed State setter contract. These findings narrow, not erase, the remaining response/preservation evidence gap.

**Updated bottom line:** Namecheap's real narrow all-active BasicDNS implementation is now integrated and locally verified; see [SDK contract update](<namecheap-sdk-contract-update.md>) and [full progress](<../PROVIDERS.md>). It is not arbitrary-zone/DDNS/inactive/metadata compatibility. Eranet is still the best next fixture-backed per-ID candidate, followed by independently verified Now.cn/Tnet.hk; all three require independent response/paging/signing/settings clarification. Neither CAS absence nor website-table omissions alone categorically block a provably preserving narrow implementation.
